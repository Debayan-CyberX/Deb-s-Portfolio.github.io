AEGIS-X

From security events to evidence-linked investigations. A SOC prototype with correlation rules, incident timelines, access controls, and an auditable response workflow.

Next.jsFastAPISQLAlchemyPostgreSQL
Source code

01The problem

Help an analyst follow the evidence behind an alert, investigate related events, and record a controlled response in one workspace.

02My implementation

I implemented the frontend, FastAPI backend, correlation logic, authentication, investigation workflow, and tests.

03Architecture

  1. 01Next.js workspace
  2. 02FastAPI + sessions
  3. 03Correlation engine
  4. 04Incidents + audit

Normalized synthetic events flow through deterministic rules into incidents, investigation context, and recorded response simulations.

04Engineering decision

Deterministic correlation creates incidents before optional AI explanations. Detection stays usable without a model key; broader coverage requires additional rules and real integrations.

05Security & reliability

Argon2 password hashing, revocable HttpOnly sessions, role checks, origin validation, and rate limiting protect application boundaries. Response actions remain explicitly simulated.

Follow the workflow

  1. Run the fictional AgriShield scenario locally: five failed sign-ins followed by a success.
  2. Follow normalized events through correlation rules to evidence-linked incidents and MITRE ATT&CK references.
  3. Inspect the timeline and relationship graph; request an evidence-grounded investigation with an offline fallback.
  4. Approve simulated isolation, review the audit trail, and export the incident report. No actual host is isolated.

06Product gallery

07Results & current boundaries

Synthetic enterprise telemetry and simulated response actions. This is a single-workspace portfolio system without live collectors, rather than a production SIEM.

Repository tests cover detection windows, authentication and roles, event idempotence, incident workflows, reports, and WebSocket delivery. The checkpoint distinguishes completed checks from pending work.

DIGITAL KYOTO / DOSSIER 02
Document security · Hackathon

Tri-Shield

Three complementary checks for document review: identifier validation, image-forensics signals, and a hash-chained audit record.

PythonFastAPIOpenCVSQLite
Source code

01The problem

Give a document reviewer a visible chain of checks instead of relying on a single identifier or image signal.

02My implementation

I built the complete application: processing pipeline, validation and forensics, audit chain, API, Streamlit interface, and tests. Teammates supported research and presentations.

03Architecture

  1. 01Streamlit reviewer
  2. 02FastAPI processing
  3. 03OCR + OpenCV
  4. 04SQLite audit chain

The review interface combines structural checks and image analysis, then records document hashes and metadata in a local audit chain.

04Engineering decision

Combine structural rules and image-forensics heuristics with a local hash chain. The approach runs offline, but compression artifacts and local storage limit what it can prove.

05Security & reliability

SHA-256 links expose changes in recorded audit entries. The chain is local and tamper-evident; it cannot prove government identity, document authenticity, or the truth of the original input.

Follow the workflow

  1. Choose a fictional clean or edited sample document in the Streamlit interface.
  2. Inspect extracted fields, Aadhaar checksum or PAN structure checks, and the image anomaly heatmap.
  3. Compare explanations and heuristic scores across clean and tampered samples.
  4. Record metadata and hashes, then simulate an audit-record edit to see chain verification fail.

06Product gallery

07Results & current boundaries

Checksums validate structure, not identity. Error Level Analysis is a heuristic that can misclassify images. The local ledger is tamper-evident, not a distributed blockchain or government identity verification.

The repository includes validator, image-forensics/scoring, and audit-chain tests. Sample verdicts demonstrate configured rules; they are not measured real-world accuracy.

DIGITAL KYOTO / DOSSIER 03
Full-stack product · Email intelligence

InboxIQ

Turn connected email conversations into a reviewable lead workflow, with opportunity detection, contextual drafts, and explicit approval before sending.

ReactTypeScriptExpressBetter AuthSupabase
Source codeLive project ↗

01The problem

Help a small business identify promising email conversations and prepare relevant next steps without losing control of outgoing messages.

02My implementation

I designed and implemented the application across the React workspace, authentication, database-backed workflows, Gmail integration, and draft-review experience.

03Architecture

  1. 01React workspace
  2. 02Express + Better Auth
  3. 03Gmail + Groq
  4. 04Supabase Postgres

Authenticated requests scope conversations, opportunities, and persisted drafts to the current user. Gmail and AI integrations are mediated by the server.

04Engineering decision

Persist drafts and require an explicit send action. When AI is unavailable, labeled rules and template drafts keep the workflow understandable, at the cost of less tailored suggestions.

05Security & reliability

OAuth state is signed, expiring, and user-bound. Queries are scoped by owner; import sizes are capped. Provider keys stay on the server. Sending requires explicit approval of the persisted draft.

Follow the workflow

  1. Connect an authorized Gmail account and sync recent conversations into the workspace.
  2. Review detected opportunities and their context; adjust lead stages and next steps.
  3. Generate or edit a contextual reply, then save and review the authoritative draft.
  4. Choose Send explicitly. The backend uses the connected account and updates delivery state after provider acceptance.

06Product gallery

07Results & current boundaries

Gmail requires account authorization. Analysis resumes while the workspace is open, rather than running continuously in the background. Sending supports one recipient and plain text, without attachments or delivery/open tracking.

Repository tests include provider simulations for ownership isolation, repeated analysis, drafts, and send-state handling. Simulated transport tests do not establish real inbox delivery.

Networking · Interactive learning

TCP/IP Simulator

Follow a configured message through the TCP/IP layers, inspect protocol headers, and explore packet encapsulation at your own pace.

JavaScriptHTMLCSSTCP/IP
Source codeLive project ↗

01The problem

Make the relationship between application messages, transport headers, IP addressing, and network-layer framing easier to explore.

02My implementation

I implemented the browser interface, protocol examples, simulation controls, validation, and packet visualization.

03Architecture

  1. 01Message + config
  2. 02Protocol model
  3. 03Layer visualizer
  4. 04Inspect + export

All simulation state stays in the browser. Protocol examples illustrate encapsulation without opening sockets or capturing real packets.

04Engineering decision

Keep the simulator entirely in the browser, with step and automatic playback. It is easy to try without setup, but modeled headers are not real captured traffic.

05Security & reliability

IP and port validation constrain the educational configuration. The simulator does not send network traffic, scan hosts, or represent a packet capture.

Follow the workflow

  1. Choose a protocol and configure a message, IP addresses, and ports.
  2. Configure the packet, then select step mode to follow each TCP/IP layer.
  3. Inspect the added headers and packet statistics; compare another protocol example.
  4. Pause, reset, or export the simulation results.

06Product gallery

07Results & current boundaries

A conceptual simulation, not a packet capture tool or implementation of a production network stack.

Try the hosted simulator and compare step mode, reset, example loading, and export behavior. The original repository contains no automated test suite.

Civic technology · Hackathon

DrainSentinel

A map-based storm-drain inspection workflow combining risk prioritization, maintenance tasks, and a traceable path to resolution.

ReactFastAPILeafletAWS adapters
Source code

01The problem

Help municipal inspection teams prioritize at-risk drains and track maintenance work through a visible operational workflow.

02My implementation

I implemented the frontend, mapping, backend services, risk and inspection workflows, and deployment code. Teammates contributed research and presentations.

03Architecture

  1. 01React + Leaflet
  2. 02FastAPI workflow
  3. 03Risk + adapters
  4. 04Storage + evidence

A mapped drain asset connects risk inputs to inspection tasks and resolution evidence. Local and AWS adapters support different demo environments.

04Engineering decision

Use explainable risk heuristics with an optional AI layer and local/cloud storage adapters. This supports a reproducible demo; real flood-risk use requires calibrated data and operational validation.

05Security & reliability

Infrastructure code defines scoped IAM, encrypted storage, private S3 defaults, and expiring upload URLs. These are configured safeguards, not proof of an active or independently audited cloud deployment.

Follow the workflow

  1. Inspect the drain map, risk levels, and the factors behind a prioritized asset.
  2. Open a drain detail and review supporting reports and inspection context.
  3. Create and progress a maintenance task through the inspection workflow.
  4. Review resolution evidence and audit history rather than treating a risk score as a final operational decision.

06Product gallery

07Results & current boundaries

The demonstration uses synthetic telemetry. Scores are not validated flood forecasts. Cloud services require configuration; infrastructure code does not imply every deployment is active.

The repository includes risk-engine, API, weather/prediction, inspection-workflow, and AWS-adapter tests. Synthetic inputs demonstrate behavior rather than field accuracy.

LibraryLens

A library discovery and reservation prototype with searchable books, detail pages, a library map, and an Android project powered by Capacitor.

ReactTypeScriptCapacitorAndroid
Source code

01The problem

Give students a compact interface for browsing books, exploring library information, and managing a sample reservation flow.

02My implementation

I implemented the complete application and Android integration. Teammates handled supporting research and presentations; the original Figma design is credited in the repository.

03Architecture

  1. 01React catalog
  2. 02Reservation state
  3. 03Local storage
  4. 04Capacitor Android

The web interface is reused inside an Android wrapper. Reservations persist locally on a device; there is no shared inventory service.

04Engineering decision

Share a React interface across web and an Android Capacitor wrapper. Local storage makes reservations easy to demonstrate, but does not synchronize stock or bookings across devices.

05Security & reliability

The prototype does not demonstrate production authentication or synchronized inventory. Sample reservation data stays in local browser storage; use fictional student information.

Follow the workflow

  1. Search the catalog by title or author and narrow results by genre.
  2. Open a book detail page and start a reservation with sample student information.
  3. Review active reservations and their expiry in the profile view.
  4. Explore the library map or open the Capacitor Android project for the mobile experience.

06Product gallery

07Results & current boundaries

Reservations are stored locally in the browser. There is no demonstrated connection to a real library inventory or shared reservation backend.

The repository has a Vite build command and Android scaffold tests. It does not include a dedicated automated test suite for the reservation workflow.
